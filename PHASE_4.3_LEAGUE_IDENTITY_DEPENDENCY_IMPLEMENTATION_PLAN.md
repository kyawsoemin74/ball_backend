## 2. Frozen Design Recap

The implementation must preserve these approved rules:

1. League Master owns provider identity.
2. FixtureSync must not create or repair League identity.
3. FixtureSync validates identity before Provider access.
4. League identity recovery belongs to the League domain.
5. Recovery has its own transaction boundary.
6. FixtureSync re-resolves identity after committed recovery.
7. Team identity retains resolve -> ensure/create -> resolve-again.
8. One unresolved League cannot abort unrelated valid League units.
9. API/Scheduler own outer transactions.
10. Provider calls occur only after local identity validation.
11. No silent identity guessing.
12. Idempotency is mandatory.

Source basis: [PHASE_4.2_LEAGUE_IDENTITY_DEPENDENCY_DESIGN_FREEZE.md](PHASE_4.2_LEAGUE_IDENTITY_DEPENDENCY_DESIGN_FREEZE.md), [app/services/fixture_sync_service.py](app/services/fixture_sync_service.py#L589-L610), [app/services/league_service.py](app/services/league_service.py#L216-L310).

## 3. Implementation Dependency Order

The implementation order is:

```text
Database/invariants decision
  -> Model/state representation decision
  -> Repository contracts
  -> Provider lookup contract
  -> League recovery SyncService
  -> LeagueService facade
  -> Scheduler/API recovery triggers
  -> FixtureSync handoff/re-resolution
  -> Verification and production gates
```

### Why this order is required

1. **Database/invariants:** determine what identity uniqueness/state can be represented without violating current schema policy.
2. **Model:** only after state/constraint needs are approved can model changes be specified.
3. **Repository:** persistence and identity conflict semantics must exist before services call them.
4. **Provider:** recovery needs a verified provider response identity; the transport contract must be explicit before orchestration.
5. **SyncService:** owns recovery sequencing, state, and provider-to-repository orchestration.
6. **Service facade:** exposes the workflow consistently to API/scheduler callers.
7. **Scheduler/API:** trigger recovery only after service contracts are stable and transaction ownership is clear.
8. **FixtureSync integration:** last among runtime changes because it consumes all upstream contracts and must preserve existing Match/Team behavior.
9. **Verification:** validates isolation, idempotency, locks, real PostgreSQL, provider behavior, and runtime startup.

Independent work: provider contract tests, repository read-only identity tests, and API response schema design can proceed in parallel after the design decisions. Dependent work: recovery service requires repository/provider contracts; FixtureSync requires recovery result semantics; scheduler/API require service result and lock contracts.

## 4. League Identity Recovery Workflow

Target runtime sequence:

```text
FixtureSync
  -> validate local League identity
  -> identity unresolved
  -> request League-domain recovery
  -> LeagueService/LeagueSyncService invokes LeagueProvider
  -> verify provider response identity
  -> LeagueRepository attaches/updates identity
  -> recovery transaction commits
  -> FixtureSync re-reads League Master
  -> validated provider identity
  -> FixtureProvider.get_fixtures(provider_id, season)
  -> normal fixture processing
```

### Ownership and outcomes

| Situation | Required behavior |
|---|---|
| Already resolved | Do not invoke recovery; re-check and request fixtures normally |
| Missing/invalid identity | FixtureSync emits a typed dependency result and invokes the League-domain recovery contract, not a repository write directly |
| Recovery provider lookup | LeagueProvider method such as existing `get_league_details(provider_id)` or an approved identity discovery method; exact discovery source is unresolved if no provider ID exists |
| Provider identity available from authoritative input | LeagueService/LeagueSyncService verifies returned provider ID/name before repository update |
| Recovery commit | Separate League recovery session/transaction commits before FixtureSync re-resolution |
| Recovery failure | No identity mutation is committed; state becomes retryable/unresolved with reason |
| Re-resolution failure after success | FixtureSync does not call fixture Provider; recovery is treated as unconfirmed and logged as a consistency failure |
| Identity conflict | No automatic overwrite; mark invalid/manual-review/retry state and preserve existing canonical ownership |

Important limitation: if only the local `league_id` exists and `provider_id` is absent, the current `LeagueProvider.get_league_details` cannot be called with a trustworthy provider ID. The implementation must choose an approved discovery source, such as an operator-supplied provider ID or an authoritative provider search contract. It must not guess by name. This is **UNRESOLVED — REQUIRES PROVIDER/DATA-DISCOVERY DECISION**.

## 5. Recovery Trigger Policy

### Trigger A - Fixture Sync

When validation finds missing/invalid identity:

1. Do not call FixtureProvider.
2. Do not mutate League or create a provider identity in the FixtureSync transaction.
3. Return or hand off a typed `IDENTITY_UNRESOLVED` result to the caller.
4. If a synchronous recovery contract is approved and has an authoritative discovery input, request League-domain recovery in a separate transaction.
5. Re-resolve after a committed recovery result.
6. Continue only after validation succeeds; otherwise isolate/fail this League/season unit.

The default plan is a recovery handoff, not an unbounded inline retry. A synchronous retry may occur once after a verified recovery commit; repeated retries belong to the recovery scheduler.

### Trigger B - Scheduler

The scheduler should discover unresolved candidates through a League-domain query, not by repeatedly running FixtureSync for every invalid League. Candidate query concept:

```sql
SELECT league_id, provider, provider_id
FROM leagues
WHERE provider IS NULL
   OR btrim(provider) = ''
   OR provider <> 'api-football'
   OR provider_id IS NULL
   OR btrim(provider_id) = '';
```

The actual implementation must add state/attempt fields or an equivalent existing durable mechanism before claiming retry eligibility. Current schema does not provide recovery state, attempt count, or next-attempt time. Therefore exact retry interval and maximum attempts are **UNRESOLVED — REQUIRES OPERATIONS DECISION**.

Frozen scheduler rules:

- one scheduler job owns identity recovery;
- candidate selection is bounded and deterministic;
- each League recovery has a per-League lock;
- retries use backoff and a terminal/manual-review state;
- success means provider identity was verified, committed, and re-read;
- failure does not invoke FixtureProvider;
- valid League fixture work is not blocked by an invalid candidate.

### Trigger C - Manual/API

The current architecture has an admin League registration endpoint at [app/api/admin_leagues.py](app/api/admin_leagues.py#L30-L95), but it requires a provider and positive provider ID. It is not an unresolved-identity recovery endpoint.

Do not invent a new endpoint in this phase. A future administrative recovery endpoint is an implementation requirement only if operations need manual discovery/approval. It must be admin-only, call LeagueService, own/coordinate the recovery transaction, and return the same typed state as scheduler recovery.

## 6. Scheduler Retry Design

### Lifecycle

```text
IDENTITY_UNRESOLVED
  -> RECOVERY_PENDING
  -> RECOVERY_RUNNING
  -> RECOVERED / IDENTITY_VALID

RECOVERY_RUNNING
  -> RECOVERY_FAILED
  -> RETRY_ELIGIBLE
  -> RECOVERY_RUNNING

RECOVERY_FAILED + max attempts/conflict
  -> MANUAL_REVIEW / IDENTITY_UNRESOLVED
```

### Required design

| Concern | Plan |
|---|---|
| Frequency | Bounded scheduled job; exact interval is unresolved until operations chooses it |
| Advisory lock | New namespaced `league_identity:<local league_id>` resource lock through `run_with_resource_lock`; exact numeric scheduler lock only if required by deployment topology |
| Candidate query | League rows in missing/invalid/retry-eligible state, bounded by `next_attempt_at` and batch limit |
| Retry eligibility | Provider/transient failures and unresolved discovery may retry; identity conflicts and invalid authoritative payloads require manual review |
| Duplicate prevention | Per-League resource lock plus durable state transition from pending to running |
| Transaction | One recovery attempt/session per League; provider call and identity write share that attempt transaction, commit only after verification |
| Provider boundary | Recovery provider call occurs only with an approved discovery input; fixture provider is never called during failed recovery |
| Success | Identity persisted, commit succeeds, fresh read confirms provider/provider ID |
| Failure | Rollback, record typed failure/attempt metadata, schedule bounded retry or manual review |
| Logging | Include League ID, provider, provider ID/null, state, attempt, lock, provider result class, transaction outcome |

If a durable state table/model is not approved, the scheduler cannot safely implement controlled retry, because current `leagues` has no attempt or next-retry fields. This is a design dependency, not permission to add schema in this phase.

## 7. Failure Isolation

### Required unit of work

- Current season endpoint: one `League + season`; unresolved identity fails that requested unit before provider access.
- Future multi-League scheduler/batch: one `League + season` provider request and transaction unit per candidate.
- Fixture payload: existing per-fixture savepoints remain for fixture-level errors, but aggregate batch commit policy must be made explicit.

For:

```text
League A unresolved
League B valid
League C valid
```

the plan requires:

```text
A -> recovery/failure state, no fixture request
B -> independent provider request and transaction
C -> independent provider request and transaction
```

No shared aggregate transaction may cause A to roll back B/C when B/C are independent operation units. This is a future batch/recovery design; the existing one-League season endpoint cannot process B/C in the same request.

## 8. API Error Contract

The current route uses fixed HTTP 200 and returns a dictionary, including the unresolved identity dictionary. The implementation plan must replace the ambiguous body-only distinction with a stable machine-readable outcome.

Required body shape, independent of final numeric status:

```json
{
  "success": false,
  "operation": "fixture_season_sync",
  "league_id": 389,
  "season": 2026,
  "state": "LEAGUE_IDENTITY_UNRESOLVED",
  "error_code": "LEAGUE_PROVIDER_IDENTITY_UNRESOLVED",
  "message": "League provider identity is unresolved; fixture provider was not called.",
  "provider_request_attempted": false,
  "inserted": 0,
  "updated": 0,
  "failed": 0,
  "recovery": {"state": "NOT_ATTEMPTED"}
}
```

Required distinctions:

| Condition | Required code/state | HTTP mapping |
|---|---|---|
| Invalid query/auth | FastAPI/auth error | Preserve existing validation/auth architecture |
| Missing/invalid League identity | `LEAGUE_PROVIDER_IDENTITY_UNRESOLVED` | Exact status unresolved; must not be silently HTTP 200 success |
| Recovery pending | `LEAGUE_IDENTITY_RECOVERY_PENDING` | Exact status unresolved; implementation/API decision |
| Provider failure after valid identity | `FIXTURE_PROVIDER_FAILURE` | Existing provider failure semantics must be reviewed |
| Empty provider response | `NO_FIXTURES_FOUND` | Existing service result can remain typed |
| DB failure | `FIXTURE_SYNC_DATABASE_FAILURE` | Exception/error handling consistent with API architecture |
| Partial unit/batch | `PARTIAL_SYNC` | Must include committed/failed/isolated counts |
| Unexpected server error | Generic server error | Existing exception handling |

The exact numeric HTTP status is **UNRESOLVED — REQUIRES API CONTRACT DECISION** because the current repository uses mixed body-return and exception patterns. The implementation must not preserve `HTTP 200 + success:false + failed:0` as the only signal for identity failure.

## 10. Transaction Boundaries

### League Recovery Transaction

```text
Recovery session begins
  -> read current League identity
  -> obtain authoritative provider identity/input
  -> LeagueProvider lookup/verification
  -> conflict/uniqueness check
  -> LeagueRepository identity update
  -> flush + fresh read
  -> commit
  -> release recovery lock
```

Rollback on provider failure, invalid response, conflict, DB failure, or commit failure. No Fixture Match work occurs in this transaction.

### Fixture Sync Transaction

```text
API/Scheduler session begins
  -> League identity validation/re-read
  -> FixtureProvider request
  -> fixture parsing
  -> Team resolve/ensure/re-resolve
  -> LeagueSeason/Venue/Referee processing
  -> Match upsert and flush
  -> commit
  -> active/cache/finalization side effects
```

Recovery and Fixture Sync must not be merged into one transaction: recovery must be independently verified and committed before a provider fixture request; failed fixture persistence must not leave an ambiguous identity mutation; separate sessions prevent a failed fixture transaction from poisoning recovery state.

## 11. Concurrency and Locking

Current shared fixture lock: `run_with_resource_lock(db, "fixture_query", "global", ...)`. Current scheduler also uses integer advisory locks such as `DAILY_FIXTURE_SYNC_LOCK_KEY`; resource locks are namespaced by `fover:sync`.

Target lock identities:

```text
League recovery: fover:sync:league_identity:<local league_id>
Fixture sync:   fover:sync:fixture_query:global       # preserve current behavior
Scheduler job:  scheduler-level lock for the recovery job, if required
```

Rules:

- Recovery lock is per League, not global, so unrelated Leagues recover concurrently.
- FixtureSync must not hold a League recovery lock across the fixture transaction unless a concurrency review proves it necessary.
- API and scheduler recovery requests for the same League contend on the same identity lock.
- The winner re-reads current identity before provider lookup; the loser re-reads after contention and treats an already-valid identity as success/no-op.
- Identity update uses repository conflict checks and database uniqueness.
- Existing daily/live fixture locks remain unchanged.

The exact numeric advisory lock key for the new job is **UNRESOLVED — REQUIRES DEPLOYMENT LOCK REGISTRY REVIEW**; use the existing namespaced resource lock unless a separate cross-process scheduler lock is required.

## 12. Idempotency

Required behavior:

| Operation | Idempotency rule |
|---|---|
| League identity recovery | Existing valid `(provider, provider_id)` returns no-op; unresolved canonical row is attached only after conflict verification |
| League Sync | Existing provider identity is reused; provider response identity must match requested identity |
| LeagueSeason Sync | Preserve unique `(league_id, season)` upsert |
| AllowedLeague | Preserve unique local `league_id`; never create a second authorization row |
| Fixture Sync | Preserve `uq_matches_provider_fixture_id` upsert |
| Team resolution | Preserve existing resolve -> ensure -> resolve-again behavior |
| Scheduler retry | Durable attempt/state plus per-League lock prevents duplicate concurrent recovery |

Recovery must never create a duplicate canonical League merely because a local row is unresolved. An identity conflict must stop mutation and enter unresolved/manual-review state.

## 13. Cache Behavior

Current League sync queues `fover:league:<id>` and `fover:leagues_grouped` invalidation for `after_commit`, and clears the queue on rollback: [app/services/league_sync_service.py](app/services/league_sync_service.py#L20-L48).

Plan:

- League identity recovery queues League-specific and grouped-League cache invalidation through the existing League service mechanism.
- Invalidation occurs **after recovery commit**, never before.
- Recovery rollback clears queued invalidation and leaves existing cache untouched.
- FixtureSync re-resolution itself does not need a new cache mechanism.
- After successful Fixture commit, preserve current active-match updates and `fover:live_matches` deletion.
- Do not invalidate Match/date/event/lineup/statistics/odds/H2H caches merely because League identity was recovered unless an existing caller proves those caches depend on League identity.
- Cache failure is logged and must not turn a committed identity into a rollback.

No new cache layer is planned.

## 15. Database Invariants

After implementation, the following must be true:

- Local League primary key remains canonical.
- `(provider, provider_id)` cannot produce duplicate canonical League identities.
- Any League eligible for provider-backed synchronization has valid provider identity.
- LeagueSeason references the intended local League and remains unique per `(league_id, season)`.
- AllowedLeague references an existing League and does not imply identity without validation.
- FixtureSync never calls FixtureProvider with unresolved identity.
- FixtureSync never persists a Match under an unresolved local League identity.
- Existing Team and Match identities remain unchanged.
- Recovery failure leaves no partial League identity mutation.
- Repeated recovery and retry converge without duplicate League, LeagueSeason, AllowedLeague, Team, or Match rows.

The current schema proves uniqueness/FKs for several relationships but does not prove the full provider identity invariant. Any schema change is outside this planning phase and requires an explicit migration decision.

## 18. Implementation Phases

### PHASE 4.3.1 - League Identity Recovery Core

**Objective:** implement League-owned, conflict-safe identity recovery contracts.  
**Files:** LeagueService, LeagueSyncService, LeagueRepository, conditional LeagueProvider/model/state files.  
**Dependencies:** authoritative provider identity discovery decision; state/attempt persistence decision.  
**Tasks:** define result/state types, verify provider response identity, attach/update atomically, no-op valid identity, reject conflicts, commit separately.  
**Verification:** unit tests for valid/missing/invalid/conflict/repeated recovery and rollback.  
**Pass:** recovery never fabricates identity and re-read confirms committed identity.  
**Fail:** duplicate identity, partial mutation, or ambiguous provider response.

### PHASE 4.3.2 - Scheduler Retry Integration

**Objective:** bounded recovery discovery and retry.  
**Files:** scheduler, monitoring, state model/migration if approved.  
**Dependencies:** Phase 4.3.1 and lock/attempt policy.  
**Tasks:** candidate query, per-League lock, state transitions, backoff, max attempts/manual review, metrics.  
**Verification:** concurrent scheduler runs and retry exhaustion tests.  
**Pass:** no uncontrolled repeated provider calls; valid Leagues continue.  
**Fail:** duplicate concurrent recovery or infinite retry.

### PHASE 4.3.3 - FixtureSync Handoff/Re-resolution

**Objective:** integrate recovery result without moving ownership into FixtureSync.  
**Files:** FixtureSyncService, FootballService facade, related tests.  
**Dependencies:** recovery result/transaction contract.  
**Tasks:** defensive validation, typed handoff, one post-commit recovery re-resolution, provider call only after valid identity, preserve Team/Match behavior.  
**Verification:** provider mock asserts zero calls before valid identity and one normal call after recovery.  
**Pass:** successful recovery resumes normal fixture flow; failed recovery isolates unit.  
**Fail:** FixtureSync writes League identity or guesses provider ID.

### PHASE 4.3.4 - API Error Contract

**Objective:** expose dependency, recovery, provider, empty, partial, and database outcomes distinctly.  
**Files:** season API route, schemas if approved, shared error mapping if existing architecture supports it.  
**Dependencies:** typed service result and API status decision.  
**Tasks:** response shape, stable error codes, rollback mapping, preserve 409 lock behavior.  
**Verification:** route tests for every outcome.  
**Pass:** callers can distinguish identity failure from provider/DB failure without parsing free-form messages.  
**Fail:** unresolved identity remains indistinguishable HTTP 200/`failed:0`.

### PHASE 4.3.5 - Concurrency + Idempotency Hardening

**Objective:** prove API/scheduler collision safety and repeat convergence.  
**Files:** recovery service/repository, resource lock integration, tests.  
**Dependencies:** phases 4.3.1-4.3.4.  
**Tasks:** same-League lock, loser re-read, unique conflict handling, retry semantics.  
**Verification:** simultaneous API/scheduler recovery and repeated runs.  
**Pass:** one canonical identity, no duplicate writes, deterministic outcomes.  
**Fail:** race-dependent identity ownership or duplicate League rows.

### PHASE 4.3.6 - Real Database Verification

**Objective:** verify transaction and constraints against disposable PostgreSQL.  
**Files:** test fixtures/scripts only; no production data.  
**Dependencies:** completed code phases and approved migrations if any.  
**Tasks:** rollback/recovery commit/re-read, unique conflicts, LeagueSeason/AllowedLeague relationships.  
**Verification:** SQL counts and transaction assertions.  
**Pass:** no partial identity state and all invariants hold.  
**Fail:** committed identity without verification or invalid relationship rows.

### PHASE 4.3.7 - Real Provider Sync Verification

**Objective:** verify authoritative League lookup and fixture request parameters in a controlled environment.

## 22. Final Implementation Readiness

**C. NOT READY - DESIGN GAP REMAINS**

The core architecture is approved and implementable in principle, but repository evidence leaves required implementation decisions unresolved:

1. No authoritative provider discovery input is defined when a local League has no provider ID; the existing provider detail method requires an ID.
2. Current schema has no durable identity recovery state, attempt count, or next-retry field.
3. Exact API status/error-code mapping is not established by current conventions.
4. Exact scheduler interval, maximum attempts, and lock registry key are not established.
5. It is unresolved whether a pre-existing LeagueSeason is required before season fixture retrieval.
6. The exact database mechanism for enforcing provider identity eligibility is not approved.

No implementation should begin until those decisions are explicitly resolved. The frozen ownership, provider boundary, separate transactions, no-guess rule, Team compatibility, and failure-isolation principles are ready to guide that decision work.
