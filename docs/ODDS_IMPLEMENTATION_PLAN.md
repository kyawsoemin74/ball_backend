# Odds Implementation Plan

**Plan status:** Planning only — no implementation authorized
**Plan basis:** Repository inspection and approved Odds design revision 2.0, 2026-10-09
**Verdict:** **READY WITH EXPLICIT BLOCKERS**

## 1. Executive Summary

The active Odds path can be updated without moving responsibilities across the frozen architecture:

```text
FootballAPIClient / OddsProvider
  -> OddsService (canonical domain normalization, validation, Myanmar conversion)
  -> OddsSyncService (write orchestration and outcome classification)
  -> OddsRepository (Odds SQL and atomic snapshot replacement)
  -> PostgreSQL

AnalyticsProjectionService / Analytics repository (Analytics-owned projection)
  -> same API/Scheduler-owned transaction as the Odds snapshot

API/Scheduler (advisory lock, commit/rollback, retry-state orchestration,
post-commit Odds-cache invalidation)
```

The plan retains the public GET response fields and current raw market display value while introducing canonical market identity in the internal validated snapshot passed to Analytics. This avoids an unapproved public response-contract change. A future API change to return canonical categories as `market` requires separate compatibility approval.

Main required changes:

- Validate bookmaker ID/name identity from evidence; use ID 11 / 1xBet only, with no Bet365 fallback.
- Canonicalize the verified bet IDs 1, 4, 5, 45; retain unknown ID/name evidence without assigning a guessed category.
- Validate the complete candidate, including finite positive odds and required Myanmar labels for IDs 4 and 5, before repository replacement.
- Align Analytics projection to the 1xBet normalized snapshot and fail the shared transaction on zero acceptance or reconciliation failure.
- Prevent immediate retries for Odds timeouts/5xx; honor 429 `Retry-After` and a shared provider cooldown.
- Persist per-match failure count and next eligible time; support exact ambiguous-commit verification and cache-recovery state.
- Keep commit/rollback in API/Scheduler and persistence SQL in the appropriate repositories.

The repository has no Odds-specific durable retry state. A dedicated persistence design and additive Alembic migration are therefore a likely dependency and require separate schema approval. No numeric retry limit, fallback cooldown, or backoff interval is specified by this plan.

### 3.2 Read flow and public contract

- `GET /api/matches/{match_id}/odds` calls `football_service.get_cached_odds`; it does not call the provider or calculate Myanmar Odds. [app/api/matches.py](../app/api/matches.py#L301-L312), [app/services/odds_service.py](../app/services/odds_service.py#L219-L254)
- On cache miss, OddsService serializes `bookmaker`, `market`, `selection`, `odd`, `myanmar_odd`, and `updated_at`. The current `market` string is `Odds.market_name`, presently copied from provider `bet.name`. Preserve these fields and current market-display semantics in this implementation unless a separately approved API change is made.
- The read path returns stored Myanmar labels verbatim. Do not add conversion to GET.
- The current cache key is built from prefix, `"match"`, local Match ID, `"odds"`: [app/cache.py](../app/cache.py#L21-L24). Cache operations stay in `CacheService`/cache utilities; invalidation remains with API/Scheduler after confirmed commit.
- No Flutter/client source was found. The client’s reliance on raw `market` values, handling of NULL Myanmar values, and response caching is unverified.

## 4. Current Behavior vs Approved Target

| Concern | Current source fact | Approved target / implementation consequence |
|---|---|---|
| Bookmaker identity | Service selects ID 11; persists response name or fallback `"1xBet"`. It does not assert that the live name corresponds to ID 11. | Use ID 11 only; verify actual ID/name from approved evidence before runtime acceptance; reject identity mismatch/missing name rather than silently labeling fallback identity; never substitute Bet365. |
| Analytics | Projection accepts only `bet365` and canonical names; active Odds passes ID-11 rows with raw names. Filter-to-zero preserves existing Analytics rows and may return success. | Narrowly align the Analytics Odds projection’s approved bookmaker filter to 1xBet and supply canonical market names. Zero accepted rows/reconciliation failure is an error in the shared transaction. Analytics owns its projection persistence. |
| Market identity | Bet IDs 1/4/5/45 are selected, but names are persisted raw. Analytics accepts canonical names. | Normalize verified IDs to `MATCH_WINNER`, `ASIAN_HANDICAP`, `GOALS_OVER_UNDER`, `CORNERS_OVER_UNDER`. Retain raw provider ID/name in diagnostics for unknowns; never guess aliases. |
| Public API | GET returns existing stored `market_name` in `market`. | Preserve response fields and raw display behavior. Keep canonical category on the internal snapshot DTO used for validation/Analytics; do not silently change the API contract. Any unavoidable stored/API-value change is a separate approval gate. |
| Myanmar | Exact raw-name gates control active conversion; IDs 4/5 required by design, 1/45 permit NULL. Current caller does not validate conversion status. | Eligibility only from verified market ID. Require complete inputs, nonempty valid labels, successful supported result for IDs 4/5; ID 1/45 NULL is expected. Conversion failure rejects whole candidate before repository call. |
| Candidate validation | Invalid values and incomplete lines can be skipped; a surviving subset can replace all prior rows. No explicit finite/positive guard. | Validate entire supported candidate before any delete/replace. Empty, invalid, incomplete, or unusable candidate preserves existing Odds and Analytics snapshots. |
| Repository | `replace_fixture_odds` deletes even when called with an empty list; active service guards its call, but repository API itself is destructive for empty input. `snapshot_matches_rows` compares keys only. | Harden repository contract to reject empty snapshots before DELETE; perform atomic replace only for a validated nonempty snapshot. Add exact snapshot verification of all expected key/value/Myanmar fields and exact set equality for ambiguous commit handling. |
| Schedule/freshness | Job interval 360 minutes; eligible status set NS/TBD/PST; 72-hour horizon; 12-hour gate uses latest row only. | Three-hour cadence, prematch only. Retain 72-hour/12-hour baselines, but freshness is satisfied only by a valid complete snapshot; a due persisted retry overrides freshness suppression, subject to provider cooldown. PST must represent future rescheduled prematch as frozen. |
| Provider retry | Shared metadata client immediately retries transport errors and 5xx; no Retry-After propagation. | Odds request must opt out of immediate timeout/5xx retries without changing unrelated provider behavior. 429 must capture/honor Retry-After and enforce provider-wide cooldown. |
| Retry state | No Odds retry-state model/repository/table is present. Existing MatchFinalization/LeagueIdentityRecovery state is owned by unrelated workflows. | Persist per-Match failure count and next eligible time in Odds-owned state; do not reuse unrelated state. Determine required migration. Persist provider-wide cooldown where shared across workers. |
| Results/monitoring | `SUCCESS` is returned by SyncService before the caller commits. Empty response has no error/status. `observe_sync` treats a dict as success unless `success == false` or `error` is present. | Use explicit classifications: `SUCCESS`, `NO_DATA`, `PROVIDER_FAILED`, `VALIDATION_FAILED`, `DB_WRITE_FAILED`, `COMMIT_UNKNOWN`, `CACHE_INVALIDATION_FAILED`. Public `SUCCESS` is only final after confirmed commit; metrics must distinguish no-data/failure and pre-commit validation from committed update. |
| Transaction/cache | API/Scheduler own commit/rollback; cache deletion follows a normal commit. Scheduler ambiguous-commit hooks are missing. Scheduler keeps cache retry IDs in memory. | Keep transaction ownership. Verify expected complete persisted snapshot in a fresh session on ambiguous commit. Invalidate only after confirmation. Track cache failure separately and persist recoverable pending invalidation so it does not require provider refetch or depend solely on process memory. |

## 9. Database and Migration Assessment

### 9.1 Existing support

- [app/models/odds.py](../app/models/odds.py#L8-L28) stores Odds snapshot rows only; it has no attempt count, next retry timestamp, provider cooldown, structured unknown-market diagnostic, or cache-pending field.
- `MatchFinalization` and `LeagueIdentityRecovery` have persisted retry concepts, but belong to different workflows and include their own terminal/attempt policies. They must not be repurposed for Odds.
- The scheduler’s `pending_odds_cache_invalidations` is an in-memory `set[int]`, not durable across worker restarts.
- No model/repository named for Odds retry state was found. Durable per-match state and provider-wide cooldown therefore likely require an additive migration.

### 9.2 Proposed schema for separate approval (not created)

Proposed `odds_refresh_state`:

- `match_id` primary key and FK to `matches.local_match_id`, `ON DELETE CASCADE`.
- `failure_count` integer, non-null, default 0, check `>= 0`.
- `next_eligible_at` timezone-aware timestamp, nullable.
- `last_outcome` / `last_error_category` bounded strings; `last_error_message` bounded/sanitized text.
- `last_diagnostic` JSON/JSONB for unknown market raw ID/name and bounded validation details; no provider credentials/full response bodies.
- `cache_invalidation_pending` boolean, non-null default false.
- `created_at`, `updated_at`; index on `next_eligible_at` (and pending invalidation if candidate volume warrants it).

Proposed `odds_provider_cooldown`:

- provider/account-scope key as primary key (exact scope must reflect the API-Football credential/quota ownership without storing a secret).
- `cooldown_until` timezone-aware timestamp, `last_http_status`, sanitized reason, `updated_at`.
- Row-level locking/atomic update so multiple workers honor one provider cooldown.

The cache-pending flag should be set atomically in the successful Odds transaction before commit. After commit, attempt cache deletion; on success clear the flag in a separate state transaction. If clearing fails, repeat deletion later (idempotent). A retry-state update after a failed Odds refresh must occur only after the snapshot transaction rolls back/closes, then re-acquire the per-Match advisory transaction lock in the new transaction to avoid races. A failed retry-state write must be surfaced; do not claim a durable retry/cooldown was recorded.

### 9.3 Migration and rollback considerations

- A new additive Alembic revision is likely required; no existing retry table is appropriate on inspected evidence. This is a **separate migration approval gate**; no migration is authored in this phase.
- No backfill is required for historical Odds snapshots. State rows can be created on first refresh attempt; defaults leave existing data untouched.
- Downgrade would drop retry/cooldown/diagnostic/pending-invalidation state, losing outstanding retry and cache-recovery work. Rollback should be coordinated and must not imply Odds rows are reverted.
- FK cascade behavior when a Match is deleted, check constraints, timestamps/timezones, JSON size/retention, indexes and provider cooldown scope require schema review.
- Deployment sequencing: apply additive schema before code that reads/writes it; code must not run against a schema lacking the approved revision. Rollback code/schema order must be explicit.
- Production data risk is low for additive empty state tables but operational risk is meaningful: dropping pending cache state or resetting cooldown/failure counts may cause repeated provider requests. Validate migration and rollback in isolated environments first.
